items:
  - question: "What is opentel-mcp?"
    answer: "opentel-mcp is a Node.js OpenTelemetry instrumentation library for Model Context Protocol (MCP) servers. Calling `instrumentMcpServer(server, options)` wraps a server's `tools/call` handler and creates an OpenTelemetry span for every tool call, detecting silent failures — `CallToolResult.isError: true` inside an otherwise-successful JSON-RPC 2.0 response — along the way."
  - question: "What is a silent failure in an MCP server?"
    answer: "A silent failure is when an MCP tool call returns a successful JSON-RPC 2.0 response, but the tool result itself carries `isError: true`. Instrumentation that only checks whether the JSON-RPC call succeeded misses this, since the failure is nested inside a successful response, not reported as a JSON-RPC-level error. See [Silent Failures](/docs/silent-failures) for the full explanation."
  - question: "How does opentel-mcp differ from the standard OpenTelemetry Node.js SDK?"
    answer: "The standard OpenTelemetry Node.js SDK has no concept of the MCP protocol and no way to see inside a `CallToolResult` payload — that's true by definition, since it's a general-purpose SDK, not MCP-aware. opentel-mcp adds MCP-specific instrumentation on top of it, including detecting `isError: true` inside successful responses and marking the span `ERROR`."
  - question: "Does opentel-mcp work with fastmcp?"
    answer: "No — fastmcp (PrefectHQ/fastmcp) is a Python framework, and opentel-mcp is a Node.js package that instruments servers built on `@modelcontextprotocol/sdk`, the JavaScript/TypeScript MCP SDK. It can't instrument a Python server directly. The connection between the two projects is narrower: while working on MCP observability, the author found and reported a silent-failure-propagation bug in fastmcp itself (PrefectHQ/fastmcp#4549, fixed in PR #4587) — that's an upstream contribution, not a compatibility claim."
  - question: "What is Deep Failure Fingerprinting?"
    answer: "Shipped in v0.4.0, Deep Failure Fingerprinting computes a stable 16-character identifier (SHA-256, truncated) for every thrown error and every `isError: true` result, so repeated occurrences of the same underlying bug group under one fingerprint instead of showing up as unrelated errors. See [Deep Failure Fingerprinting](/docs/deep-fingerprinting)."
  - question: "Does opentel-mcp add high-cardinality labels to my metrics?"
    answer: "No. A frozen `METRIC_SAFE_ATTRIBUTES` array — containing only `mcp.failure.category` (8 values) and `mcp.failure.origin` (3 values), 24 combinations maximum — is the only path by which a fingerprint-derived value can reach a metric label. The unbounded ones (`fingerprint`, `signature`, `error_class`) are structurally confined to span attributes; there's no code path that attaches them to a counter or histogram."
  - question: "Can opentel-mcp cause my server to crash?"
    answer: "No code path in opentel-mcp is designed to throw into your application. `computeFingerprint()` in particular runs inside its own top-level try/catch and falls back to a fixed identity (`0000000000000000`) rather than raising an exception if anything about the fingerprinting pipeline fails."
  - question: "What Node.js versions are supported?"
    answer: "Node.js 20 and newer, per the package's `engines` field."
  - question: "Does opentel-mcp work with SigNoz, Jaeger, Honeycomb, and Grafana Tempo?"
    answer: "Yes. opentel-mcp emits standard OpenTelemetry spans and metrics through `@opentelemetry/api`, so it works with any OTLP-compatible backend — that includes SigNoz, Jaeger, Honeycomb, and Grafana Tempo, along with any other backend that speaks the OpenTelemetry protocol."
  - question: "How do I export metrics to Prometheus?"
    answer: "Register `@opentelemetry/exporter-prometheus` (or any Prometheus-compatible exporter) as your `MeterProvider`'s reader — nothing about `instrumentMcpServer()` changes. See [Metrics](/docs/metrics) for a wiring example and PromQL query."
  - question: "Does opentel-mcp instrument resources and prompts, or just tools?"
    answer: "Just tools, as of v0.4.0 — specifically the `tools/call` request handler. `instrumentMcpServer()` only wraps the handler registered for `CallToolRequestSchema`; requests for `resources/*` or `prompts/*` pass through unwrapped."
  - question: "Does opentel-mcp support the low-level Server API, or only McpServer?"
    answer: "Both. `instrumentMcpServer()` accepts a low-level `Server` (from `@modelcontextprotocol/sdk/server/index.js`) or a high-level `McpServer` (from `@modelcontextprotocol/sdk/server/mcp.js`) and detects which one it was given. See [API Reference](/docs/api-reference)."
  - question: "What happens if I call instrumentMcpServer() more than once on the same server?"
    answer: "Nothing extra — it's idempotent. The second and subsequent calls are a no-op, whether made on the same object or interchangeably on an `McpServer` and the inner `Server` it wraps."
  - question: "What happens if I register a tool handler before calling instrumentMcpServer()?"
    answer: "That handler never gets wrapped — it was registered before the trap was set. `instrumentMcpServer()` must run before any `.tool()`/`.registerTool()` call (McpServer) or `server.setRequestHandler(CallToolRequestSchema, ...)` call (low-level Server); see [Getting Started](/docs/getting-started)."
  - question: "Do I need to install @opentelemetry/api separately?"
    answer: "Yes. `@opentelemetry/api` is a peer dependency (`^1.9.0` or newer) — install it alongside opentel-mcp: `npm install opentel-mcp @opentelemetry/api`."
  - question: "Does opentel-mcp create a TracerProvider for me?"
    answer: "Only if you set `setupNodeSdk: true`, which is meant for local development — it creates a `NodeTracerProvider` that prints to stderr. By default (`setupNodeSdk: false`), opentel-mcp emits spans through whatever `TracerProvider` your application already registered globally, or drops them silently if none has been registered — it never overrides your own OpenTelemetry setup."
  - question: "Can I disable opentel-mcp entirely without removing the code?"
    answer: "Yes — pass `{ enabled: false }` to `instrumentMcpServer()` and it becomes a complete no-op."
  - question: "Can I disable metrics but keep tracing?"
    answer: "Yes — pass `{ enableMetrics: false }`. Tracing is unaffected either way; metrics are already a zero-overhead no-op until your application registers a `MeterProvider`, so this is for opting out even when one is registered."
  - question: "Can I disable Deep Failure Fingerprinting?"
    answer: "Yes — pass `{ fingerprinting: false }`. It's on by default (`true`)."
  - question: "Is opentel-mcp free and open source?"
    answer: "Yes, MIT licensed."
  - question: "How does opentel-mcp track LLM cost on MCP tool calls?"
    answer: "Shipped in v0.5.0. When a tool result carries recognizable usage data, `applyCostAttribution()` extracts input/output token counts and the model name, then prices them against a `PricingTable` (`DEFAULT_PRICING` by default). It sets `mcp.tool.tokens.*`, `mcp.tool.model`, and — when the model resolves in the pricing table — `mcp.tool.cost.usd`/`mcp.tool.cost.currency` span attributes, plus two counters: `mcp.tool.tokens.total` and `mcp.tool.cost.total`. See [Cost & Token Attribution](/docs/cost-tracking)."
  - question: "Which LLM providers does opentel-mcp recognize automatically?"
    answer: "`defaultExtractor` recognizes Anthropic, OpenAI, and Bedrock usage field-name conventions directly, plus the MCP `_meta.usage` extension point and JSON-in-text inside `content[0].text`. `DEFAULT_PRICING` prices models across five providers — Anthropic, OpenAI, Google, AWS Bedrock, and DeepSeek — so once a tool result's usage lands in one of the recognized field-name shapes (DeepSeek's API is OpenAI-compatible, for example), it gets priced. See [Cost & Token Attribution](/docs/cost-tracking) for the full detection order."
  - question: "Does opentel-mcp enforce budgets or just observe them?"
    answer: "Observability only. `costTracking.budget` (`perSessionUsd`/`perToolUsd`) never blocks a tool call and never throws — crossing a limit only sets `mcp.tool.cost.budget_exceeded: true` and `mcp.tool.cost.budget_scope` on the span. Enforcing the limit is left entirely to whatever consumes that span attribute downstream."
  - question: "How accurate is opentel-mcp's default pricing table?"
    answer: "`DEFAULT_PRICING` was last verified 2026-07-29 and covers 15+ models across five providers as a convenience default, not a maintained price list. Provider pricing changes frequently; production users must override `costTracking.pricingTable` for accurate cost figures."
